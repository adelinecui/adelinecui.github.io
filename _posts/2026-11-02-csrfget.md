## 一、题目信息
- 平台：Pikachu
- 分类：CSRF -> csrf(get)
- 难度：简单
- 通关标识：通过伪造 URL 链接，在未填写表单的情况下成功修改个人信息

## 二、考点
1. CSRF（跨站请求伪造）原理
2. GET 请求方式下的 CSRF 漏洞利用
3. 浏览器 Cookie 机制与身份认证

## 三、题目内容
系统提供了一个登录和个人信息修改功能。修改个人信息时，请求通过 GET 方式发送，且后端未进行任何 CSRF Token 校验或 Referer 来源检查。攻击者可以构造恶意链接，诱导受害者点击，从而在受害者不知情的情况下修改其个人信息。

## 四、解题步骤

**1. 正常登录并抓取请求**
使用账号 `pikachu` / 密码 `123456` 登录系统。进入“个人信息中心”，点击“修改个人信息”。正常修改一项内容（如手机号），点击提交，并在 Burp Suite 中抓取该请求。

发现请求为 GET 方式，参数全部暴露在 URL 中：
```http
GET /pikachu/vul/csrf/csrfget/csrf_get_edit.php?sex=girl&phonenum=18810191009&add=chain&email=vince%40pikachu.com&submit=submit HTTP/1.1
Host: 127.0.0.1
```

**2. 构造恶意 URL**
复制上述完整的 URL 路径。在浏览器新标签页中直接访问该 URL，并将 `phonenum` 参数修改为任意数字（例如 `666666`）：
```text
http://127.0.0.1/pikachu/vul/csrf/csrfget/csrf_get_edit.php?sex=girl&phonenum=666666&add=chain&email=vince%40pikachu.com&submit=submit
```

**3. 验证漏洞**
按下回车访问该链接。页面提示修改成功。返回个人信息中心刷新页面，发现手机号已被成功修改为 `666666`。整个攻击过程中，攻击者只需诱导受害者点击链接即可完成操作，无需获取受害者的账号密码。

## 五、知识点解析
1. **CSRF 原理**：跨站请求伪造（Cross-Site Request Forgery）。攻击者利用受害者已经登录的合法身份（浏览器会自动携带 Cookie），在受害者不知情的情况下，向服务器发送恶意请求。服务器无法区分请求是受害者主动发出的，还是被诱导发出的。
2. **GET 型 CSRF**：因为修改信息的请求使用了 GET 方法，参数都在 URL 中。攻击者只需构造一个包含恶意参数的 URL，诱导受害者点击，请求就会被浏览器自动发送，从而实施攻击。

## 六、总结与防御
**本题总结**：
系统未校验请求来源，且敏感操作使用 GET 请求，导致攻击者可以通过伪造 URL 链接轻易实施 CSRF 攻击。

**安全防御建议**：
- **使用 CSRF Token**：在表单中加入随机的、一次性使用的 Token，服务器验证 Token 的正确性，这是最有效的防御方式。
- **改用 POST 请求**：敏感操作（如修改密码、转账）不应使用 GET 请求，应使用 POST 请求。
- **校验 Referer**：检查请求头中的 `Referer` 字段，确保请求来源于本站域内。
- **设置 SameSite Cookie**：将 Cookie 属性设置为 `SameSite=Lax` 或 `Strict`，防止跨站携带 Cookie。
