## 一、题目信息
- 平台：SQLi-Labs
- 分类：Web - SQL Injection
- 难度：中等
- 通关标识：登录后识别出 `Cookie` 中的 `uname` 字段存在注入，使用 UNION 联合查询爆出所有账号密码。

## 二、大白话原理讲解
这关的柜员（数据库）不仅看你的脸（表单输入），还看你的“手环”（Cookie）。
登录成功后，服务器会给你发一个 `Cookie`，里面写着 `uname=admin`。之后你每次刷新页面，后台都会直接读取这个 `uname` 的值，去数据库里查你是谁，并且把查到的结果打印在屏幕上。

因为后台没对 `Cookie` 里的内容做过滤，你只要修改 `Cookie` 的值，就等于直接对数据库下达了指令。

## 三、解题步骤

**1. 正常登录，获取 Cookie**
在登录框输入 `admin` / `admin`，点击登录。页面会显示登录成功，并直接回显出你的 `Cookie` 信息。

**2. 使用 F12 修改 Cookie**
*   按 `F12` 打开开发者工具，找到 `Application`（应用） -> `Cookies` -> 你的域名（如 `http://127.0.0.1`）。
*   找到 `Name` 为 `uname` 的 Cookie，双击它的 `Value`（原值为 `admin`）。
*   将其修改为测试 Payload：
    ```text
    -1' union select 1,2,3 --+
    ```
*   按下回车保存，然后按 `F5` 刷新页面。

**3. 验证回显点**
刷新后，页面下方回显：
`Your Login name:2`
`Your Password:3`
这说明 UNION 联合查询成功，回显点在 2 和 3 的位置。

**4. 终极拖库**
再次修改 Cookie 的 `uname` 值：
```text
-1' union select 1,group_concat(username,0x3a,password),3 from users --+
```
刷新页面，`Your Login name:` 后面成功爆出所有用户的账号密码。

## 四、踩坑记录与复盘
1. **Cookie 注入的隐蔽性**
   很多人只盯着登录框，其实登录成功后，后台为了维持会话，往往会利用 Cookie 查库，这就是漏洞所在。
2. **F12 修改 Cookie 的便捷性**
   相比于配置 Burp Suite 抓包，F12 修改后直接刷新页面，效率极高，非常适合本地靶场练习。
3. **注释符的选择**
   在 Cookie 中，`--+` 容易因为编码问题失效，最好使用 `#` 作为注释符（如果在 URL 中直接传参，`#` 需要编码为 `%23`，但在 F12 的 Cookie 编辑框里直接输入即可）。

## 五、总结与防御
**本题总结**：
Less-20 是 Header 注入篇的经典关卡。只要用户输入被拼接到 SQL 语句中，无论是表单还是 Cookie，都是潜在的注入点。

**安全防御建议**：
- **不要信任 Cookie**：客户端 Cookie 极易被篡改，绝不能直接将 Cookie 中的明文内容拼进 SQL 查询。
- **加密与签名**：对存储用户身份的 Cookie 进行加密和签名验证。
- **预编译语句**：彻底解决 SQL 注入问题。
