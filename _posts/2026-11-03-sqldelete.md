## 一、题目信息
- 平台：Pikachu
- 分类：SQL-Inject -> "delete"注入
- 难度：简单
- 通关标识：修改删除请求的参数，触发 `or 1=1` 条件，成功删除全表数据

## 二、考点
1. DELETE 语句中的 SQL 注入
2. 逻辑运算符 `or 1=1` 的破坏性利用
3. URL 编码绕过（空格替换）

## 三、题目内容
页面提供了一个留言板，用户可以发表留言并删除自己的留言。删除留言时，前端会向后端发送包含留言 ID 的 GET 请求。后端直接将该 ID 拼接到 DELETE 语句中执行。

## 四、解题步骤

**1. 发布留言**
在留言板输入内容并提交。页面下方出现留言和“删除”按钮。

**2. 抓取删除请求**
开启 Burp Suite 拦截。点击“删除”按钮。抓取到的请求大概如下：
```http
GET /pikachu/vul/sqli/sqli_del.php?id=53 HTTP/1.1
Host: 127.0.0.1
```

**3. 修改参数注入**
将 `id=53` 修改为恒真条件。由于 URL 中不允许包含空格，必须使用 `+` 或 `%20` 进行 URL 编码：
```text
id=1+or+1=1
```
点击 `Forward` 放行请求。

**4. 验证结果**
回到网页刷新，发现留言板里的所有留言都被删除了。后端执行的实际 SQL 语句变成了 `DELETE FROM message WHERE id = 1 or 1=1;`，导致全表数据被清空。

## 五、知识点解析
1. **DELETE 注入**：增删改查（CRUD）操作中，只要存在参数拼接，都可能存在注入。DELETE 注入具有极强的破坏性。
2. **URL 编码与空格绕过**：HTTP 协议不允许 URL 中出现未编码的空格。攻击者常使用 `+` 或 `%20` 替代空格，以绕过 WAF 或服务器的解析限制。

## 六、总结与防御
**本题总结**：
本题展示了破坏型 SQL 注入的威力。由于后端没有对 `id` 参数进行类型检查或预编译，导致攻击者可以轻易地构造 `or 1=1` 来清空全表。

**安全防御建议**：
- **预编译语句**：使用 PDO 预编译，防止 SQL 拼接。
- **强制类型转换**：对于 ID 参数，必须在后端强制转换为整数（如 `intval($id)`），禁止传入非数字字符。
- **最小权限原则**：应用数据库账号应严格限制权限，避免拥有 DROP、DELETE 等危险操作的全局权限。
