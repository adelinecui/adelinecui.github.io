## 一、题目信息
- 平台：SQLi-Labs
- 分类：Web - SQL Injection
- 难度：困难（思维转折点）
- 通关标识：利用“二次注入”原理，先注册一个带有恶意 Payload 的用户名（如 `admin'#`），登录后利用修改密码功能，触发 Payload 从而重置真正的 `admin` 账户密码。

## 二、大白话原理讲解
之前的关卡，你输入 Payload，后台立刻拿去查库，页面立刻报错或回显。这叫“一次注入”。
但这一关，后台的代码非常“死脑筋”：

1. **防住了第一次**：当你注册新用户时，如果你输入了带引号的恶意名字 `admin'#`，后台的代码会把引号转义（变成 `admin\'#`），然后安全地存进数据库。此时页面风平浪静。
2. **栽在了第二次**：当你登录后点击“修改密码”时，后台从数据库里把当初存进去的名字取出来。**因为是从自己数据库里拿的，后台认为绝对安全，直接把它拼进了修改密码的 SQL 语句里。**
3. **炸弹引爆**：此时，那个曾经被转义、后来又复原的单引号，直接闭合了新语句，导致 `#` 后面的 `AND password=...` 全部被注释掉。结果就是，你修改了 `admin` 的密码，而不是你自己那个奇葩名字的密码！

## 三、解题步骤

**1. 注册“带雷”的恶意用户**
*   点击注册页面，用户名填入 `admin'#`，密码填入 `123456`。
*   注册成功。此时后台拼出的 SQL 是 `INSERT INTO users (username, password) VALUES ('admin\'#', '123456')`。引号被转义，安全写入。

**2. 登录并触发炸弹**
*   用 `admin'#` / `123456` 登录系统。页面显示 `YOU ARE LOGGED IN AS admin'#`。
*   进入修改密码页面，将新密码设置为 `hacked`（当前密码填 `123456`）。点击 `Reset`。

**3. 见证奇迹（修改密码的执行原理）**
此时，后台从数据库里取出你的用户名（变成了 `admin'#`），并拼出了这样一条修改密码的 SQL 语句：
```sql
UPDATE users SET password = 'hacked' WHERE username = 'admin'#' AND password = '123456';
```
因为 `#` 是注释符，后面的条件全被忽略了。所以，实际执行的 SQL 是：
```sql
UPDATE users SET password = 'hacked' WHERE username = 'admin';
```
**结果**：真正的管理员 `admin` 的密码被强制改成了 `hacked`。

**4. 验证结果**
*   退出当前账户（Logout）。
*   用真正的管理员账户 `admin` / `hacked` 登录，成功登录，通关。

## 四、知识点解析
1. **二次注入（Second Order Injection）**：Payload 不会在第一次提交时立刻触发，而是被存储到数据库中，在后续的查询或操作中才被触发。
2. **为什么转义失效了？**：第一次入库时进行了转义，但数据库存取的本质是字符串。当后台从数据库取出数据时，它并不会再次进行转义，而是直接作为“可信数据”拼接到了新的 SQL 语句中，导致了注入。
3. **注入危害**：这种注入不仅能爆数据，还能直接修改其他用户的密码，危害极大。

## 五、总结与防御
**本题总结**：
Less-24 是 SQLi-Labs 里含金量极高的一关，它打破了“漏洞一定在输入框”的固有思维，展示了数据在“入库”和“出库”之间产生的信任断层。

**安全防御建议**：
- **处处不信任**：无论是用户的直接输入，还是从数据库里取出来的数据，在拼接到 SQL 语句前，必须使用预编译语句（PDO/MySQLi）。
- **最小权限**：数据库账号不要使用 root，避免注入后一次性被拿走所有权限。
